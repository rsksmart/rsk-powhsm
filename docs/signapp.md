# powHSM signer authorization tool for Ledger

## Foreword

The tool described in this document is designed exclusively for the Ledger version of
powHSM. Therefore, all the information contained herein must be interpreted as applying
exclusively to this implementation.

The SGX version of powHSM has got its own independent authorization tool, described in
[this document](./signmigration.md).

## Abstract

This document describes the usage of `signapp`, the middleware tool that serves the
purpose of generating and signing authorization files for Signer versions. For details on
the signer authorization scheme itself (i.e., the "N of M" signatures requirement, the
message format and the encoding used for the digests to be signed), please refer to the
[signer authorization documentation](./signer-authorization.md).

The tool supports five operations, which can be split into two groups, depending on their
intended use:

- Production operations:
  - `message`: computes the message to be signed for a given Signer version, and
    optionally generates an unsigned authorization file for it.
  - `eth`: signs an authorization with a Ledger device running the Ethereum app.
  - `manual`: adds an externally generated signature (e.g., one obtained from MetaMask or
    MyEtherWallet) to an authorization file.
- Testing and build operations:
  - `hash`: computes a Ledger application's (e.g., `signer.hex`) hash.
  - `key`: signs an authorization with a manually input private key. *This operation is
    intended for testing purposes only and must never be used in production.*

## Running the tool

The tool can be run from within a middleware development environment terminal (see [the
middleware documentation](../middleware/README.md) for details on setting one up), by
means of the `signapp.py` script within the `middleware` directory.

A binary build of the tool, `signapp`, is also included in every Ledger distribution. The
binary accepts the exact same operations and options as the script. Throughout the rest of
the document, we will use an example binary for the examples, located at `tools/signapp`.
For instance, to print the tool's built-in help, issue:

```
> tools/signapp --help
```

## Options

The following is the complete list of options. Note that each option is only meaningful
for some of the operations (see each operation's section for details):

- `-a`, `--app`: path to the Signer application (the `.hex` file generated by the build).
  Used to compute the application hash.
- `-i`, `--iteration`: the Signer iteration, either as a decimal or as a hexadecimal
  number prefixed with `0x`. Must be a 16-bit unsigned integer.
- `-f`, `--file`: an existing signer authorization file from which to read the Signer
  version (`message` operation only). Cannot be combined with `-a` or `-i`.
- `-o`, `--output`: the signer authorization file to create or update (or, for the `eth`
  operation together with `-b`, the file to which to save the public key).
- `-k`, `--key`: a 32-byte hex-encoded private key (`key` operation only).
- `-p`, `--path`: the BIP32 derivation path of the signing key (`eth` operation only).
  Defaults to `m/44'/60'/0'/0/0`.
- `-b`, `--pubkey`: retrieve and save the device's public key instead of signing (`eth`
  operation only).
- `-g`, `--signature`: the externally generated signature to add (`manual` operation
  only). See [supported signature formats](#supported-signature-formats).
- `-s`, `--signer`: the expected signer of the given signature, either as a hex-encoded
  address or public key (`manual` operation only).
- `-v`, `--verbose`: enable verbose mode (useful for debugging the communication with a
  Ledger device).

## The signer authorization file

All of the signing operations read from and write to a signer authorization file. This is
a JSON file that specifies the Signer version being authorized (its hash and iteration)
along with the signatures collected so far. For example:

```json
{
  "version": 1,
  "signer": {
    "hash": "e1baa18564fc0c2c70ac4019609c6db643adbf12711c8b319f838e6a74b0da2c",
    "iteration": 45
  },
  "signatures": [
    "3045022100cbd7...",
    "3044022057a1..."
  ]
}
```

Every Ledger distribution includes an unsigned signer authorization file under
`firmware/signer_auth.json`, authorizing the Signer version included in the distribution.
This is the file that must be fully signed before upgrading an existing device (see the
[Ledger distribution documentation](../dist/ledger/README.md) for details on the upgrade
process). The minimum number of signatures needed is the threshold (N/2+1) for the total
number of authorizers (N) in the UI authorizers header file specified at build time.

Signatures are always stored DER-encoded and normalized to their low-S form, irrespective
of the format in which they were given. Also, each authorizer is counted at most once:
attempting to add a second signature by an authorizer that has already signed (be it an
exact copy, a different encoding of the same signature or a brand new signature) is
rejected.

## Testing and build operations

### Computing a Signer hash (`hash`)

The `hash` operation computes and prints the hash of a given Signer application. This is
the hash that the UI checks against its `authorized_signer_hash` before allowing the
Signer to be installed and run. It is used by the distribution build process to report
the hashes of the built applications, but it can also be used to independently verify
that a given Signer build matches the hash in a signer authorization file.

To compute the hash of a Signer application, issue:

```
> tools/signapp hash -a /path/to/app.hex
```

which should output something like:

```
Computing hash...
Computed hash: e1baa18564fc0c2c70ac4019609c6db643adbf12711c8b319f838e6a74b0da2c
```

### Signing with a private key (`key`)

**This operation is not to be used in production under any circumstances.** It requires
the private key of an authorizer to be input in plain text on the command line, which
defeats the entire purpose of safekeeping said key. Its sole intended use is for testing,
e.g., to sign authorizations for Signer builds against a UI built with a set of test
authorizers whose private keys are known.

The `key` operation signs a signer authorization with a given private key and adds the
resulting signature to the signer authorization file given. If the file does not exist,
it is first created from the given Signer application and iteration. To sign with a
private key, issue:

```
> tools/signapp key -o /path/to/signer_auth.json -k <private_key>
```

or, if the authorization file doesn't exist yet:

```
> tools/signapp key -o /path/to/signer_auth.json -k <private_key> -a /path/to/app.hex -i <iteration>
```

where `<private_key>` is the 32-byte hex-encoded private key (with or without the `0x`
prefix). The operation can be repeated with each of the test authorizers' keys until the
signature threshold is met.

## Production operations

The production operations are designed so that holders of the authorizing private keys
can sign a Signer version by any of the following means, without ever exposing said keys:

- With a Ledger device running the Ethereum app, connected to the machine running the tool
  (`eth` operation).
- With any third-party wallet that supports Ethereum's standard message signing (e.g.,
  MetaMask, MyEtherWallet, MyCrypto, Etherscan), on any machine. The
  message to sign is obtained with the `message` operation, and the resulting signature
  is then added to the authorization file with the `manual` operation.

Both means can be freely combined to gather the signatures for a single authorization.

### Signing with a Ledger device (`eth`)

The `eth` operation signs a signer authorization with a Ledger device running the
Ethereum app and adds the resulting signature to the signer authorization file given. If
the file does not exist, it is first created from the given Signer application and
iteration (in the same way as for the `key` operation).

Before starting, connect the device to the machine running the tool, unlock it and open
the Ethereum app. Then, issue:

```
> tools/signapp eth -o /path/to/signer_auth.json
```

or, to sign with a key other than the one corresponding to the default derivation path
(`m/44'/60'/0'/0/0`):

```
> tools/signapp eth -o /path/to/signer_auth.json -p "<path>"
```

The tool first outputs the address and public key corresponding to the derivation path
used, so that the authorizer can verify that the expected address is being used for
signing. It then sends the message to the device for signing and outputs the message along
with its digests:

```
Check that the device shows the following message (or one of the digests) before approval:
    Message:                                          RSK_powHSM_signer_e1baa18564fc0c2c70ac4019609c6db643adbf12711c8b319f838e6a74b0da2c_iteration_45
    Digest (app >= 1.22.3, if hash display enabled):  0xaab6e50fff0522d6bbf5c4bd0aaf789bbc295d00ce71d1f81294f4fb0a4945bb
    Digest (app <= 1.9.19):                           8E61ADD23E0D2BDBA258DB6B66420B667D0B7980B8BD856EE6AC620D11BD68F5
```

The authorizer must check that the device displays either the message or the digest that
corresponds to the Ethereum app version installed, and only then approve the signature on
the device. The tool verifies the signature obtained from the device against the
retrieved public key before adding it to the signer authorization file.

#### Retrieving the public key

Authorizers can also use the `eth` operation to retrieve the public key corresponding to
their signing key, e.g., in order to include it in the UI authorizers header file. To do
this, issue:

```
> tools/signapp eth -b -o /path/to/pubkey.txt
```

optionally specifying a derivation path with `-p`. The tool outputs the address and
public key, and saves the hex-encoded public key to the given output file. No signing
takes place.

### Computing the authorization message (`message`)

The `message` operation computes the message that authorizers must sign for a given
Signer version. The Signer version can be specified either by means of the Signer
application and iteration, or by means of an existing signer authorization file. To
compute the message from the Signer application and iteration, issue:

```
> tools/signapp message -a /path/to/app.hex -i <iteration>
```

or, to compute it from an existing signer authorization file (e.g., the one included in a
distribution), issue:

```
> tools/signapp message -f /path/to/signer_auth.json
```

The output should look like the following:

```
Message to sign: copy and paste exactly, as a single line, into your
wallet's 'sign message' feature - e.g., MyEtherWallet, MetaMask:

    RSK_powHSM_signer_e1baa18564fc0c2c70ac4019609c6db643adbf12711c8b319f838e6a74b0da2c_iteration_45

Your wallet automatically adds the standard Ethereum signed message prefix.
Do NOT include it yourself.


For reference only (do NOT paste these into your wallet):

    Full message: \x19Ethereum Signed Message:\n95RSK_powHSM_signer_e1baa18564fc0c2c70ac4019609c6db643adbf12711c8b319f838e6a74b0da2c_iteration_45
    Digest (keccak256):        0xaab6e50fff0522d6bbf5c4bd0aaf789bbc295d00ce71d1f81294f4fb0a4945bb
```

The message under "Message to sign" is the one that must be pasted, verbatim, into the
third-party wallet. The full message and digest are given for reference only, e.g., to
compare against the digest a wallet or hardware device displays before signing.

Alternatively, if an output path is given, then instead of printing the message, the
operation writes a new, unsigned signer authorization file for the given Signer version.
This is how the distribution build process generates the unsigned
`firmware/signer_auth.json` file. For example:

```
> tools/signapp message -a /path/to/app.hex -i <iteration> -o /path/to/signer_auth.json
```

*Important*: the output file is always overwritten with an unsigned authorization. In
particular, issuing the operation with `-f` and `-o` pointing to the same file discards
any signatures collected so far.

### Adding an external signature (`manual`)

The `manual` operation adds an externally generated signature to an existing signer
authorization file. The typical flow for an authorizer using a third-party wallet is as
follows:

1. Obtain the message to sign using the `message` operation (see [the corresponding
   section](#computing-the-authorization-message-message)).
2. Sign the message using the wallet's "sign message" feature.
3. Add the resulting signature to the signer authorization file using the `manual`
   operation.

To add a signature, issue:

```
> tools/signapp manual -o /path/to/signer_auth.json -g <signature> -s <expected_signer>
```

where `<signature>` is the signature (see the supported formats below) and
`<expected_signer>` is the address or public key of the authorizer that is supposed to
have produced it.

The tool verifies the given signature against the authorization message for the Signer
version in the signer authorization file, and outputs the detected signature format and
signer address. For example:

```
Opening signer authorization file /path/to/signer_auth.json...
Verifying signature...
Signature format: r||s||v
Signer address: 0x1563915e194D8CfBA1943570603F7606A3115508
Signer matches the expected signer
Adding signature...
Signer authorization saved to /path/to/signer_auth.json
```

#### Supported signature formats

The signature can be given in any of the following formats:

- A hex-encoded, DER-encoded signature.
- A hex-encoded 65-byte `r||s||v` signature, with `v` being either `27`/`28` or `0`/`1`.
  This is the format output by e.g. MetaMask, MyEtherWallet and Ledger.
- A signed message JSON, as output by e.g. MyEtherWallet, MyCrypto or Etherscan. This
  is an object containing at least a `msg` field with the signed message (either as plain
  text or hex-encoded) and a `sig` field with a 65-byte `r||s||v` signature. If the
  object also contains an `address` field, it must match the signature's signer. The
  signed message must match the authorization message exactly.

Any of the above can be given either inline or as a path to a file containing it. Giving
a path to a file is especially convenient for signed message JSONs, which would otherwise
need to be quoted on the command line.

#### Verifying the signer

Giving the expected signer with `-s` is optional, but strongly recommended. When given,
the signature is rejected unless it was produced by that signer. When not given, the
tool still outputs the signer address along with a warning, and it is up to the operator
to check that address against the expected authorizer.

Please note that a DER-encoded signature does not, by itself, identify a single signer:
up to two candidate addresses can be recovered from it, and the tool outputs both. Using
the `r||s||v` or signed message JSON formats is therefore preferable whenever available.
